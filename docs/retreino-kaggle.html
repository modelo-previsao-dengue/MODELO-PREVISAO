Bloqueador 1 · vazamento do alvo

O DROP_COLS remove cinco colunas e deixa passar duas que o dataset novo introduziu. A pior é risco_surto_t4_com_vazamento: ela é o próprio alvo binado em quatro faixas, com correlação de Spearman de 0,863 com notificacoes_t4.

Essa coluna existe só para medir de quanto era a inflação do vazamento temporal. Como feature, ela entrega a resposta ao modelo.

O que te salva de publicar um resultado falso é um acidente. A outra coluna que passa, threshold_source, é texto — o XGBoost lança ValueError antes de treinar. Se você "resolver" isso com um select_dtypes(include=np.number), o texto some, o vazamento fica, e o modelo passa a entregar métricas excelentes e sem sentido. Use lista de exclusão explícita.

A correção
NUNCA_FEATURE = [
    "notificacoes_t4",               # o alvo
    "risco_surto_t4",                # alvo da classificação
    "risco_surto_t4_com_vazamento",  # o alvo binado — Spearman 0,863
    "threshold_source",              # texto; quebra o fit
    "ibge_municipio", "ano", "semana_epidemiologica",
]

Bloqueador 3 · o walk-forward falha, e em silêncio

A última célula tem três defeitos. Os dois primeiros lançam exceção; o terceiro é o perigoso, porque não lança nada.

LinhaProblema
**study.best_paramsstudy nunca é definido — a célula do Optuna foi substituída por KNOWN_BEST. NameError.
early_stopping_rounds=20Removido do fit() no XGBoost 2.0+; é parâmetro do construtor. TypeError.
TRAIN_MIN_ANOS = 5O recorte tem 4 anos em train+val (2019–2022). Nenhum fold é gerado, cv_df sai vazio e a média vira NaN — sem erro nenhum na tela.

Problemas menores, que ainda assim mudam os números

PontoPor quê
Sem log1pTreina em contagem crua, então um município com 3.000 casos numa semana domina o treino. O pipeline local treina em log1p e volta com expm1 — os seus números não são comparáveis às tabelas do TCC.
KNOWN_BEST · MAE 2,795Veio do dataset antigo, com outro conjunto de features. Como referência não vale mais. Os hiperparâmetros reais do braço e1_sinan_inmet estão no notebook corrigido.
Nenhum baselineSem a linha de persistência não há como afirmar que o modelo aprendeu algo. No recorte a persistência dá R²_orig 0,400 contra 0,390 do melhor XGBoost.
Não usa feature_schema.csvSem ele não dá para separar sinan de sinan+inmet — que é a pergunta central do trabalho.
load_dataset(…).to_pandas()Converte via Arrow mantendo as duas cópias vivas. No E2, com 6,1 milhões de linhas, dobra a memória. hf_hub_download + read_parquet é mais enxuto.
device="cuda" fixoVálido no XGBoost 2.0+ e bom para o E1. Mas a sessão de GPU do Kaggle tem menos RAM que a de CPU, e o E2 teve pico medido de 9 GB — para ele, prefira CPU.

Referência para saber se deu certo — braço e1_sinan_inmet, teste 2023: MAE 7,935 · R²_orig 0,390 · R²_log 0,707. Diferenças pequenas são esperadas (GPU e CPU mudam a ordem de soma em ponto flutuante). Um MAE muito menor que isso é sinal de vazamento, não de sucesso.

from kaggle_secrets import UserSecretsClient
import pandas as pd
from huggingface_hub import hf_hub_download

REPO_ID  = "thiagorfreitas/dengue-tcc2-data"
HF_TOKEN = UserSecretsClient().get_secret("HF_TOKEN")

EXPERIMENTO = ""   # "" | "e2/" | "mesorregiao/" | "uf/"
DEVICE = "cuda" if EXPERIMENTO != "e2/" else "cpu"

def baixar(nome, ext="parquet"):
    caminho = hf_hub_download(
        repo_id=REPO_ID,
        filename=f"data/model_ready/{EXPERIMENTO}{nome}.{ext}",
        repo_type="dataset", token=HF_TOKEN,
    )
    return pd.read_parquet(caminho) if ext == "parquet" else pd.read_csv(caminho)

df_train, df_val, df_test = baixar("train"), baixar("val"), baixar("test")
schema = baixar("feature_schema", "csv")

print(f"train {len(df_train):,} | val {len(df_val):,} | test {len(df_test):,}")

Treinar e avaliar

Separar os braços, com checagem de vazamento

Features vêm do schema, e o assert é a rede de segurança
FEATS = {
    "sinan":       schema.loc[schema.origem == "sinan", "feature"].tolist(),
    "sinan_inmet": schema["feature"].tolist(),
}
for nome, fs in FEATS.items():
    FEATS[nome] = [f for f in fs
                   if f not in NUNCA_FEATURE and f in df_train.columns]

# Nenhuma coluna de texto pode sobrar, nenhuma proibida pode entrar.
for nome, fs in FEATS.items():
    assert not [c for c in fs if df_train[c].dtype == object]
    assert not [c for c in fs if c in NUNCA_FEATURE]
print("Checagem de vazamento: OK")

Treinar

Alvo em log1p, previsão volta com expm1
import numpy as np, xgboost as xgb

FIXOS = dict(tree_method="hist", device=DEVICE, random_state=42,
             n_estimators=2000, early_stopping_rounds=50)

# Do braço e1_sinan_inmet, 30 trials de Optuna sobre o treino inteiro.
BEST_PARAMS = {
    "max_depth": 11, "learning_rate": 0.0156,
    "subsample": 0.561, "colsample_bytree": 0.365,
    "min_child_weight": 93, "reg_alpha": 2.051,
    "reg_lambda": 0.0171, "gamma": 0.579,
}

def treinar(feats):
    m = xgb.XGBRegressor(**BEST_PARAMS, **FIXOS)
    m.fit(df_train[feats], np.log1p(df_train["notificacoes_t4"]),
          eval_set=[(df_val[feats], np.log1p(df_val["notificacoes_t4"]))],
          verbose=False)
    return m

pred = np.expm1(m.predict(df_test[feats]))   # desfaça a transformação!

Reportar R² sem desfazer o log1p dá um número diferente e mais otimista — foi o erro do relatório anterior. R²_log e R²_orig são medidas distintas e as duas devem aparecer na tabela.

Baselines — obrigatórios, e rodam primeiro

Nenhum resultado de XGBoost deve ser reportado sem eles ao lado. No recorte municipal a persistência dá R²_orig de 0,400 contra 0,390 do melhor modelo: sem essa linha não dá para saber se o modelo aprendeu algo além da autocorrelação.

Persistência e sazonal
serie = pd.concat([df_train, df_val, df_test], ignore_index=True).sort_values(
    ["ibge_municipio", "ano", "semana_epidemiologica"])

# Persistência: repete o valor de hoje quatro semanas à frente
pred_persistencia = df_test["notificacoes"]

# Sazonal: o alvo da mesma semana no ano anterior
anterior = serie[["ibge_municipio","ano","semana_epidemiologica","notificacoes_t4"]].copy()
anterior["ano"] += 1
pred_sazonal = df_test.merge(
    anterior.rename(columns={"notificacoes_t4": "pred"}),

Armadilhas

Crítico · notebooks em colab/

Os três notebooks filtram apenas o Distrito Federal com DF_CODE = "5300108". Isso não é viável com o recorte novo: o DF tem 1 município, e sobram 157 linhas de treino para 178 features. Overfitting garantido, sem nenhum erro na tela.

Duas saídas: remova o filtro e treine nas 6 UFs, ou use EXPERIMENTO = "e2/", que cobre 2000–2023 e dá ao DF cerca de 1.250 linhas de treino — mas sem clima, porque o E2 é SINAN-only.

O que não repetir dos notebooks antigos

Prática antigaPor que está errada
Recalcular percentis de riscoVazamento temporal. Infla o F1 macro em até 0,11 no nível de UF. Use o risk_thresholds.csv que veio pronto.
TUNE_SAMPLE = 500_000Hiperparâmetros ótimos dependem do tamanho da amostra. Tunar em 500 mil e treinar em milhões entrega parâmetros de outro problema.
SAMPLE_SIZE = 50000 no SHAPExplica um modelo que não é o entregue.

risco_surto_t4_com_vazamentoExiste só para medir a inflação do vazamento. Nunca como alvo de produção nem como feature.
select_dtypes(include=np.number)Parece resolver o erro de coluna de texto, mas só esconde o vazamento: a coluna numérica que carrega o alvo continua entrando.
